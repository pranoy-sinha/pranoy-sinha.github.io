Retail Industry Bot POC

An agentic AI chatbot that lets retail staff query live order, inventory, and customer data using natural language — with an enterprise-grade pattern to ensure customer PII never reaches the AI model.

RoleFull Stack Architect & Developer
PlatformAWS EC2 · Nginx · GitHub Actions
DomainRetail Operations
TypeAI / MCP Agentic POC

The Problem

Retail staff spending 20+ minutes per shift hunting through dashboards for basic answers

The retail client's operations team needed to answer questions like "what's the stock level for SKU-4821?", "how many orders are pending dispatch in the North region?" and "show me returns from last Tuesday" — all requiring separate dashboard logins and SQL knowledge.

The goal was a conversational interface where staff could ask questions in plain English and receive accurate, live answers from the PostgreSQL database — without any SQL or dashboard navigation.

Critical Constraint: Customer PII (names, addresses, phone numbers, email) must never be sent to the OpenAI API. GDPR and internal data policy required all external AI calls to operate on anonymised identifiers only.

Architecture

MCP Server as the intelligent data access layer

1
React Chat UI (Claude-style interface)A clean streaming chat interface built in React with SSE (Server-Sent Events) for real-time response streaming. Users type questions; responses stream token by token.
2
FastAPI Orchestration LayerReceives the user message, manages conversation history, calls the AI model with the appropriate tools available, and routes tool call results back through the agentic loop until the model signals it has a final answer.
3
MCP Server (Tool Definitions)Exposes typed tools: get_order_by_id(order_id), get_stock_level(sku), list_pending_dispatch(region, date_range). Each tool returns only the fields needed — never full customer records.
4
ID-Based Lazy Loading (PII Protection)The AI model is given only numeric IDs in its context. When it needs customer details, the MCP tool fetches only the specific fields requested (e.g. city, not name+email+phone). Full PII records are assembled server-side and presented to the user — never sent to OpenAI.
5
PostgreSQL Retail DatabaseNormalised retail schema: orders, order_items, customers, products, inventory, regions. MCP tools use parameterised queries exclusively — no dynamic SQL construction.

Key Challenges

Engineering the PII boundary correctly

  • 🔒
    Preventing PII leakage through the agentic loopEarly versions allowed the model to request full customer objects. The fix was strict tool schema design: no tool returns name, email, phone, or address. Customer identity is always represented as customer_id in AI context, with display-layer enrichment handled post-response server-side.
  • 🔄
    Agentic loop termination — model not knowing when to stopGPT-4o-mini occasionally called tools in circles (fetching the same order twice). Fixed by adding a maximum tool call depth limit of 8 and a loop-detection check that identifies repeated (tool, argument) pairs within a conversation turn.
  • ⚡
    SSE streaming dropped on Nginx reverse proxyNginx buffered the SSE stream, causing the UI to receive responses in one burst rather than streaming. Fixed by adding X-Accel-Buffering: no and proxy_buffering off to the Nginx location block for the /stream endpoint.
