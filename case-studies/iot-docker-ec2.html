IoT POC — Docker / Kubernetes on EC2

Containerising an IoT telemetry stack with Docker Compose and AWS ECR, building a CI/CD pipeline that automatically rebuilds and redeploys on every push — as a stepping stone toward AWS IoT Core and MSK.

RoleCloud & DevOps Architect
PlatformAWS EC2 · ECR · IAM
DomainIndustrial IoT
TypeContainerisation & CI/CD

The Problem

An IoT stack that was impossible to deploy consistently across environments

The IoT pipeline (MQTT broker, Kafka, data consumer, Node.js simulator) was running as bare processes on EC2 with manual start scripts. Every environment change meant SSH-ing in, stopping processes, pulling code, and restarting — with no consistency, no rollback, and no visibility into what version was actually running.

The goal: containerise the entire stack, push images to AWS ECR, and have GitHub Actions automatically build, push, and redeploy on every merge to main — with a clear path toward managed AWS IoT Core and MSK in Phase 2.

Architecture

ECR-backed Docker Compose with GitHub Actions CI/CD

1
Dockerise each serviceIndividual Dockerfiles for: MQTT broker (Eclipse Mosquitto), Kafka + Zookeeper (Bitnami images), Python data consumer, Node.js device simulator, and a React dashboard. Each image tagged with Git SHA for traceability.
2
AWS ECR private registryOne ECR repository per service. IAM role attached to EC2 instance with ecr:GetAuthorizationToken, ecr:BatchGetImage, ecr:GetDownloadUrlForLayer permissions. GitHub Actions runner uses OIDC federation — no long-lived AWS keys stored in secrets.
3
GitHub Actions CI/CD pipelineOn push to main: (1) build images, (2) push to ECR with both :latest and :{git-sha} tags, (3) SSH to EC2 and run docker-compose pull followed by docker-compose up -d. Zero-downtime rolling restart for stateless services.
4
docker-compose.yml migration from local builds to ECR referencesReplaced build: . directives with image: {account}.dkr.ecr.ap-south-1.amazonaws.com/{service}:latest throughout. Added a pre-pull step that authenticates ECR before compose runs.
5
DynamoDB for device state persistenceDevice telemetry snapshots written to DynamoDB on every cycle. No persistent volume required for the simulator container — state survives container restarts via DynamoDB reads on startup.

Key Challenges

IAM, ECR auth, and docker-compose ordering

  • 🔑
    ECR authentication expiring mid-pipelineECR tokens expire after 12 hours. The GitHub Actions pipeline was caching credentials and failing on long-running jobs. Fixed by adding a fresh aws ecr get-login-password call at the start of every deploy step, not just once per workflow.
  • 📦
    Kafka not ready when consumer container starteddocker-compose depends_on only waits for container start, not service readiness. The Kafka consumer crashed on startup because Kafka wasn't yet accepting connections. Fixed with a healthcheck on the Kafka container and condition: service_healthy in depends_on.
  • 🌐
    MQTT broker unreachable from simulator after containerisationThe simulator used localhost:1883 hardcoded. Inside Docker, containers communicate via service names. Fixed by replacing localhost with the docker-compose service name mqtt-broker and using Docker's internal DNS.
