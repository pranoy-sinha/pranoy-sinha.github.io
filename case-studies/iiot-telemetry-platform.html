IIoT Telemetry Platform

Designing a fault-tolerant Industrial IoT data pipeline — from raw sensor MQTT events to hourly analytics — with a self-healing PostgreSQL HA cluster at its core.

RoleCloud & Data Architect
PlatformAWS EC2 · ap-south-1
DomainIndustrial IoT / Manufacturing
TypePOC → Production Pipeline

The Problem

Sensor data arriving faster than a single database could handle — with zero tolerance for data loss

Industrial sensors (DEMOHW0-1 and DEMOHW0-2) emit telemetry every few seconds — temperature, pressure, vibration, operational state. The existing setup wrote directly to a single PostgreSQL instance with no replication, no buffering, and no failover. Any database restart meant lost telemetry during the window.

The business needed a platform that could ingest high-frequency sensor data reliably, survive database failures without data loss, and surface hourly aggregations for maintenance and operations dashboards.

Core Requirement: Zero data loss during planned or unplanned database downtime. Automated failover under 30 seconds. Hourly IoT aggregations delivered to the analytics layer on schedule.

Architecture

Three-tier pipeline: ingest → buffer → store → analyse

1
MQTT Broker (Mosquitto)Sensors publish telemetry to a local Mosquitto broker over MQTT. Python subscribers consume events and forward to Kafka. Keeps sensor firmware simple — no Kafka client needed on device.
2
Apache Kafka (Docker on EC2)Kafka acts as the durable buffer between ingestion and storage. Even if the downstream database is unavailable, events are retained in Kafka partitions and consumed once the DB recovers. Topic: iot-telemetry, 3 partitions, 7-day retention.
3
PostgreSQL 17 HA Cluster (Patroni + etcd + HAProxy)Three-node PostgreSQL cluster: 1 primary + 2 replicas. Patroni manages leader election via etcd. HAProxy routes writes to the current primary and reads to replicas. Automatic failover in under 30 seconds.
4
pgBackRest S3 Backups with Glacier TieringContinuous WAL archiving to S3. Daily full backups with 30-day retention in S3 Standard, automatically tiered to Glacier after 7 days. Recovery point objective (RPO) under 5 minutes.
5
Apache Airflow + PySpark AnalyticsAirflow DAG runs hourly, triggering a PySpark job that reads raw telemetry from TimescaleDB hypertables, computes aggregations (min/max/avg per sensor per hour), and writes to the analytics schema consumed by dashboards.

Key Challenges

What nearly derailed the project

  • ⚡
    Split-brain risk during network partitionWithout careful etcd quorum configuration, a network blip between EC2 instances could cause both nodes to believe they are primary. Resolved by enforcing strict quorum (majority of etcd nodes must agree) and adding a DCS timeout before any failover begins.
  • 💾
    WAL slot exhaustion during Kafka lagDuring a Kafka consumer outage, unconsumed WAL slots grew unbounded, threatening to fill the EC2 disk. Fixed by setting max_slot_wal_keep_size and adding a CloudWatch alarm on WAL directory size.
  • ⏱️
    Airflow DAG timing drift on hourly aggregationsPySpark jobs occasionally ran longer than 60 minutes, causing the next DAG run to queue and pile up. Resolved by adding task timeout enforcement, dynamic backfill detection, and a maximum active runs limit of 1.
  • 🌐
    HAProxy health check false positivesHAProxy marked the primary as unhealthy during a long VACUUM operation (high I/O), triggering unnecessary failover. Fixed by tuning the health check endpoint to use pg_is_in_recovery() directly via Patroni's REST API rather than a TCP connection check.
