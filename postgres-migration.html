120GB PostgreSQL Logical Replication Migration

Moving a live 120GB+ production PostgreSQL database from AWS EC2 to Hostinger VPS with zero downtime — navigating OID mismatches, WAL slot exhaustion, partition table replica identity failures, and disk space constraints.

RoleDatabase & DevOps Engineer
Database Size120GB+ (rsb_proddb)
Migration MethodLogical Replication
TypeZero-Downtime DB Migration

The Problem

A production database that couldn't afford an hour of downtime — let alone a weekend

rsb_proddb was a 120GB+ PostgreSQL 14 database on AWS EC2 (ap-south-1) serving a live production application. The client needed to migrate to Hostinger VPS to reduce infrastructure costs — but the application had no maintenance window available. Any downtime meant lost transactions and customer-facing errors.

The standard approach — pg_dump and restore — would require 4–6 hours of downtime for a database this size. Logical replication was the only viable path: replicate changes continuously from source to target, then cut over with seconds of downtime at the moment of switchover.

The risk: Logical replication in PostgreSQL has strict requirements around replica identity, partition tables, sequences, and OIDs — any one of which can silently cause replication to lag or fail, without obvious error messages.

Migration Approach

Six phases — the wrong order would be catastrophic

1
Schema migration first (pg_dump schema-only)Exported schema (DDL only) from source and applied to target. This ensures tables, indexes, constraints, and sequences exist before replication starts — replication cannot create tables, only replicate rows.
2
Set replica identity on all tablesLogical replication requires REPLICA IDENTITY FULL or a primary key on every replicated table. Several legacy tables had neither. Applied REPLICA IDENTITY FULL to those tables — with the trade-off of larger WAL records for updates and deletes.
3
Create publication on source and subscription on targetCREATE PUBLICATION rsb_pub FOR ALL TABLES on source. CREATE SUBSCRIPTION rsb_sub on target pointing to source connection string. PostgreSQL begins copying initial table data (table sync phase) before streaming live WAL changes.
4
Monitor replication lag until caught upMonitored pg_stat_replication.write_lag and pg_replication_slots on source. Waited for lag to reach near-zero (under 100ms) across all tables before scheduling cutover.
5
Cutover — application config switch + sequence syncPut application into maintenance mode (30 seconds), synced all sequences manually (sequences do not replicate), updated application DATABASE_URL to point to target, removed maintenance mode. Total application downtime: 47 seconds.
6
Post-migration: nightly pg_dump + rsync backup pipelineBuilt a shell script that runs pg_dump at 02:00 IST daily, compresses with gzip, rsyncs to a remote backup server, and sends an SMTP alert (success or failure) to the DBA team.

Key Challenges

Four problems that nearly derailed the migration

  • 🔢
    OID mismatches breaking foreign key constraints on targetpg_dump schema-only doesn't preserve OIDs. Several system catalog references used OIDs internally (custom types, certain constraints). Fixed by using pg_dump with --no-oid and reviewing all custom type definitions manually before applying to target.
  • 💾
    WAL slot exhaustion filling EC2 diskThe replication slot on source retains WAL until the subscriber confirms receipt. A 4-hour network interruption caused the slot to hold 18GB of WAL, nearly filling the EC2 disk. Added max_slot_wal_keep_size = 10GB to postgresql.conf and a CloudWatch alarm on disk utilisation.
  • 📊
    Partition tables not replicating — silent failurePostgreSQL logical replication does not automatically replicate partition child tables — only the parent. Tables with monthly partitions (audit_log_2024_01, audit_log_2024_02 etc.) were silently excluded from replication. Fixed by explicitly listing all partition children in the publication, and adding a pre-migration script to auto-generate the partition list.
  • 🌐
    pg_hba.conf blocking replication connectionSource EC2 security group allowed the target VPS IP, but pg_hba.conf was missing the replication entry for the target IP. The subscription silently failed to connect. Fixed by adding: host replication rsb_repl_user {target_ip}/32 md5 to pg_hba.conf and reloading PostgreSQL.
