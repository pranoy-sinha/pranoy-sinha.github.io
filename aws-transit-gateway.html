AWS Transit Gateway Inter-Region Peering

Designing and provisioning multi-region AWS network infrastructure with Terraform — connecting Mumbai and Hyderabad VPCs via Transit Gateway, with private SSM access and a modular IaC pattern built to scale.

RoleCloud Infrastructure Architect
PlatformAWS ap-south-1 & ap-south-2
DomainNetwork Infrastructure / IaC
TypeTerraform Infrastructure Module

The Problem

Two regional workloads that needed to talk — privately, without a public internet hop

The organisation had workloads in AWS Mumbai (ap-south-1) — production application servers and databases — and was expanding to Hyderabad (ap-south-2) for disaster recovery and a secondary processing tier. Services in both regions needed to communicate over private IPs without traversing the public internet.

Additionally, EC2 instances in private subnets (no public IP, no bastion host) needed to be managed via AWS Systems Manager Session Manager — which requires VPC endpoints to reach the SSM, SSM Messages, and EC2 Messages services privately.

Constraint: All infrastructure must be 100% Terraform-managed — no console clicks. The module must be reusable: adding a third region should require only a new module instantiation, not changes to existing code.

Architecture

Hub-and-spoke Transit Gateway topology

1
VPC Module — reusable per regionA Terraform module provisions a complete VPC: CIDR block, public and private subnets across 2 AZs, Internet Gateway, NAT Gateway (per AZ for HA), and route tables. Called once per region with different CIDR ranges to avoid overlap.
2
Transit Gateway per regionOne TGW in Mumbai, one in Hyderabad. Each TGW has a route table. VPC attachments connect the regional VPCs to their local TGW. Route propagation enabled so VPC routes are automatically shared.
3
Inter-region TGW Peeringaws_ec2_transit_gateway_peering_attachment connects Mumbai TGW to Hyderabad TGW. The peering attachment must be accepted in the peer region — handled via a cross-region provider alias in Terraform (provider = aws.hyderabad).
4
VPC Endpoints for SSM on private subnetsThree Interface endpoints per VPC: com.amazonaws.{region}.ssm, com.amazonaws.{region}.ssmmessages, com.amazonaws.{region}.ec2messages. Attached to private subnet route tables. EC2 instances in private subnets can now be accessed via SSM without a public IP or bastion.
5
Security Groups with least-privilege rulesApplication security groups allow traffic only from the TGW attachment CIDRs, not from 0.0.0.0/0. SSM endpoint security group allows HTTPS (443) inbound from the VPC CIDR only.

Key Challenges

Cross-region Terraform is non-trivial

  • 🌍
    Cross-region provider aliasing in TerraformResources in different regions must use provider aliases. The TGW peering acceptance resource lives in ap-south-2 but is triggered by the attachment created in ap-south-1. Required careful use of provider = aws.ap_south_2 on the acceptance resource and explicit depends_on to sequence creation correctly.
  • 🛣️
    Route propagation not covering all subnetsAfter TGW attachment, only the main route table received propagated routes. Private subnets used a custom route table that wasn't associated with the TGW route propagation. Fixed by explicitly associating the custom route table with the TGW attachment and adding propagation there.
  • ⏳
    TGW peering attachment state managementInter-region TGW peering has an async acceptance step. Terraform's aws_ec2_transit_gateway_peering_attachment_accepter must wait for the attachment to reach 'available' state. Added explicit timeouts and a terraform refresh step in the CI pipeline to handle the propagation delay.
